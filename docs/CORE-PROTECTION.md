# Защита ядра приложения

«Защитить ядро» — это не одна галочка, поэтому начнём с того, от чего именно
защищаемся. Без модели угроз любая мера превращается в театр.

## От кого защищаемся

| Противник                                    | Что ему доступно                        | Что делает Kivora                                                                 |
| -------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| Пассивный наблюдатель сети                    | Трафик                                  | TLS + сквозное шифрование: видны только метаданные соединения                      |
| Взломанный или недобросовестный сервер        | Вся база и весь трафик                  | Не может читать сообщения; подмена предключа ловится подписью                       |
| Кража базы данных                             | `meta.log`, `blobs.dat`                 | Только шифротекст; пароли — Argon2id; токены — HMAC, а не сами токены               |
| Кража ноутбука (выключенного)                 | Файлы профиля                           | Ключи зашифрованы паролем + секретом ОС; троттлинг подбора                          |
| Скрипт, внедрённый в веб-слой (XSS)           | DOM и IPC приложения                    | CSP без `unsafe-inline`; минимальные разрешения Tauri; нет доступа к ФС и оболочке   |
| Вредоносный участник чата                     | Обычный клиент и API                    | Сервер отбрасывает ключи для чужих устройств; членство проверяется на каждом вызове  |
| Полностью скомпрометированное устройство      | Всё                                     | **Ничего.** Честно: это не решается на этом уровне                                   |
| Сервер, встающий в середину **звонка**         | Сигнализация WebRTC                     | **Пока ничего.** Отпечатки DTLS идут через сервер и вручную не сверяются              |

Последние две строки важны. Мера, которая якобы защищает от противника с правами
пользователя на его же машине, — это обычно обман. А звонки в этой версии
сознательно слабее переписки: было оговорено «первоначально в открытом виде», и
вместо того чтобы нарисовать замочек, здесь написано, где именно проходит
граница. Довести звонки до уровня переписки — это сверка отпечатка DTLS через
уже проверенный текстовый канал; она не сделана.

Отдельно про **проверку ключей в переписке**: клиент помнит сверенные отпечатки и
поднимает красное предупреждение, когда ключ ранее проверенного устройства
изменился. Молчаливое принятие нового ключа — самый удобный вход для сервера, и
именно его здесь нет; подробности в [CRYPTO.md](CRYPTO.md).

## Ядро на сервере

### Сетевой периметр (`internal/guard`)

* **Ограничение частоты** — токенное ведро на IP, в процессе, без Redis и без
  горутины на клиента. `X-Forwarded-For` учитывается, только если оператор явно
  сказал, что впереди доверенный прокси: иначе один заголовок обходит лимит.
* **Заголовки безопасности** — CSP без `unsafe-inline` (клиент не содержит
  инлайновых скриптов), `X-Frame-Options: DENY`, `nosniff`, `no-referrer`,
  запрет геолокации, платежей и USB. Камера, микрофон и захват экрана разрешены
  **только своему источнику** (`self`), потому что этим пользуются звонки:
  запретить их полностью выглядит строже, но ломает звонки молча — браузер
  отклоняет `getUserMedia` по нарушению политики, ничего не спросив у человека.
  Мера, которая ничего не защищает и ломает функцию, — это не строгость.
* **Кеширование статики** зависит от имени файла: «навсегда, immutable» только
  для имён с хешем содержимого. Обещать это для стабильного `main.js` значит
  оставить всех, кто уже заходил, на старой сборке после обновления.
* **Ограничение тела запроса** — до чтения в память.
* **Перехват паник** — один плохой запрос не роняет процесс, стек не утекает
  клиенту.
* **CORS** — только перечисленные источники. Учётные данные ходят заголовком
  `Authorization`, а не cookie, поэтому чужой origin не проедет на живой сессии.

### Аутентификация

* Пароли — Argon2id, параметры в конфиге.
* Вход в несуществующий аккаунт тратит **столько же** времени, сколько вход с
  неверным паролем: по времени ответа нельзя узнать, какие логины существуют.
* Токены — 32 случайных байта, в базе только HMAC на серверном секрете.
* Отзыв устройства сразу удаляет его сессии — иначе живой токен свёл бы отзыв на нет.
* Идентификатор устройства берётся **из сессии**, никогда из заголовка. Иначе
  украденный токен позволял бы притвориться чужим устройством и собрать его ключи.

### Авторизация

Каждый вызов проверяет членство. Особо:

* `GET /channels/{id}/devices` — только участникам, иначе это перепись устройств.
* `POST /channels/{id}/messages` — сервер **отбрасывает** ключи для устройств не
  из чата. Без этого отправитель мог бы завернуть ключ постороннему.
* Сигнальные события звонка (`call.ring`, `call.join`, `call.flags`,
  `call.decline`, `call.leave`, `call.signal`) — каждое проверяет членство.
  `call.leave` эту проверку когда-то не делал: утечки данных это не давало, но
  позволяло любому авторизованному сокету заставить сервер разослать
  широковещательное событие в чужой канал.
* `POST /keys/backfill` — только на свои устройства. Иначе это было бы депонирование
  ключей на сервере, ровно то, ради чего сквозное шифрование и существует.
* `GET /uploads/{id}` — только участнику канала, которому принадлежит файл.
  Знание идентификатора не даёт доступа: «неугадываемая ссылка» — это не
  разрешение.
* Ветки (`parentId`) — отдельный список участников. Членство в родительской
  группе **не** даёт доступа к ветке ни в одном обработчике.

### Загрузки

Файл в сквозном чате приходит уже шифротекстом, но сервер всё равно обращается с
ним как с враждебными байтами:

* Тип отбраковывается по списку: `text/html`, `application/javascript`,
  `image/svg+xml`, `application/xhtml+xml` не принимаются — все четыре
  исполняются в браузере.
* Аватар дополнительно сверяется с **сигнатурой файла**, а не с тем, что написал
  клиент в `mime`.
* Отдача помечена `application/octet-stream`, `Content-Disposition: attachment` и
  `X-Content-Type-Options: nosniff`. Даже если что-то проскочит, браузер это не
  выполнит.
* Размер ограничен до чтения в память (`KIVORA_MAX_FILE_MB`,
  `KIVORA_MAX_AVATAR_KB`).

Единственный контент, который сервер видит открытым, — аватары; почему так и чем
за это платим, написано в [CRYPTO.md](CRYPTO.md#аватары), а не спрятано.

### Админ-панель

Панель управления — обычно самая крупная дыра в мессенджере: «посмотреть чат
пользователя» превращает всю криптографию в декорацию. Здесь такой ручки нет и
не может быть — сообщения на сервере зашифрованы, и админ-обработчикам просто
нечего показать.

Что панель отдаёт: счётчики, ряды за 7 дней, список пользователей с числом
устройств и признаком «онлайн», список чатов с типом и числом участников,
политику установки и состояние процесса. Что она **не** отдаёт: ни одного
сообщения, ни одного завёрнутого ключа, ни одного вложения.

Управляющих действий два — выдать/снять права и заблокировать аккаунт
(блокировка сразу гасит сессии). Последний администратор не может ни разжаловать,
ни заблокировать себя: установка без администратора — это установка, которую
некому чинить.

### Политика шифров

`KIVORA_ALLOWED_SUITES` перечисляет допустимые наборы; `KIVORA_REQUIRE_E2E=true`
запрещает незашифрованные каналы вовсе. Идентификаторы проверяются по грамматике,
а не по списку: сервер не должен знать ваши алгоритмы, чтобы их пропустить.

### Целостность хранилища

Каждая запись журнала защищена CRC32; битый хвост обрезается при старте.
Уплотнение идёт через временные файлы и `rename`, поэтому падение во время него
оставляет прежнюю рабочую базу.

## Ядро в приложении

Здесь «ядро» — это буквально код за границей IPC, куда веб-слой не дотягивается.
Правило одно: **скрипт внутри WebView не должен получить ничего сверх того, что
он получил бы в браузере.**

### 1. Секрет устройства в хранилище ОС

Хранилище ключей шифруется ключом, выведенным из пароля **и** 32-байтного секрета,
который лежит в Credential Manager (Windows) или Secret Service / kwallet (Linux).

Что это даёт: скопировать каталог профиля и подбирать пароль офлайн больше нельзя
— нужен ещё и элемент хранилища ОС, привязанный к сеансу пользователя.

Если рабочего хранилища нет (бывает на минималистичных сборках Linux), ядро
кладёт секрет в файл профиля с правами `0600` и **сообщает об этом в интерфейсе**.
Заявлять защиту, которой нет, хуже, чем её не иметь.

### 2. Троттлинг подбора вне досягаемости веб-слоя

Счётчик неудачных попыток живёт в файле, которым владеет Rust-ядро. Очистка
данных сайта его не сбрасывает. Первые три ошибки бесплатны, дальше задержка
растёт геометрически до пятнадцати минут: опечатка почти незаметна, перебор на
скорости невозможен.

### 3. Минимальные разрешения

`desktop/src-tauri/capabilities/default.json` перечисляет всё, что окну можно.
Там нет разрешений на файловую систему, оболочку, запуск процессов и произвольный
HTTP. Внедрённый скрипт не читает `~/.ssh` не потому, что не додумался, а потому
что такой команды не существует.

### 4. Строгая CSP и отсутствие devtools в релизе

CSP запрещает `unsafe-inline`, `unsafe-eval` и любые внешние источники.
`assetProtocol` выключен. Инструменты разработчика открываются только в отладочной
сборке: девелоперская консоль в мессенджере — подарок любой социальной инженерии.

### 5. Крипты в Rust нет — намеренно

Соблазн «продублировать шифрование в нативном коде для надёжности» приводит к
двум реализациям, которые однажды разойдутся. Вывод ключей и шифрование остаются
в `packages/kivora-crypto`, а ядро занимается тем, чего браузер не умеет.

### 6. Один экземпляр и очистка памяти

Плагин `single-instance` не даёт запустить вторую копию со своим взглядом на то же
хранилище. Секреты в Rust обёрнуты в `Zeroize` и затираются при выходе из области
видимости.

## Ядро в браузере

Браузер даёт меньше, и делать вид, что это не так, не нужно.

* Закрытые ключи лежат зашифрованными: PBKDF2-SHA256 600 000 итераций +
  AES-256-GCM. В `localStorage` нет ничего, что открывается без пароля.
* Перезагрузка вкладки требует пароля. Это цена отсутствия ключа наготове.
* Скрипт, выполняющийся в этом origin, читает разблокированный ключ. От этого
  защищает CSP — и то, что клиент не подключает ни одной сторонней библиотеки в
  рантайме.
* Кнопка «Выйти и стереть ключи» удаляет хранилище и, в десктопе, элемент
  хранилища ОС.

## Что оператор должен сделать сам

Kivora не может закрыть это за вас:

1. **TLS.** Ставьте Caddy или nginx перед сервером; готовые конфиги — в `deploy/`.
   Без TLS сквозное шифрование остаётся, но метаданные и токены идут открыто.
2. **`KIVORA_TRUST_PROXY=true` только при реальном прокси.** Иначе ограничение
   частоты обходится заголовком.
3. **Закрытая или инвайт-регистрация** на приватном сервере:
   `KIVORA_REGISTRATION=invite` + `KIVORA_INVITE_CODES=...`.
4. **Права на каталог данных** — `0700`. Сервер создаёт его так, но проверьте
   после переноса.
5. **Резервные копии.** Копия `meta.log` и `blobs.dat` бесполезна для чтения
   сообщений (там шифротекст), но потеря — это потеря истории.
6. **Обновления.** Следите за релизами: это единственная мера от ошибок в самом
   коде.

## Проверить, что защита работает

```sh
cd server && go test -race ./...        # членство, лимиты, заголовки, хранилище
cd packages/kivora-crypto && npm test    # свойства протокола и вектора RFC
```

Отдельно стоит прочитать `internal/api/handlers_chat.go`: в `handleSend` нет ни
одной ветки, которая читает, преобразует или логирует `Body`. Это проверяется
глазами за минуту — и именно так и должно проверяться главное заявление системы.
